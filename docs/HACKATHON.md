# Hackathon plan and log

Track: **Indie developer**. Theme: **Push the Frontier**. Kickoff Mon 26 Oct 2026 12:00 PM EDT. Submission due **Wed 4 Nov 2026, 9:00 PM EDT**. Demo-ready target: Mon 2 Nov.

## The product

Design a whole office from scratch, in words. See [DESIGN.md](DESIGN.md) for the demo test, the pipeline and the honesty rules.

## Schedule

- Propose-and-repair loop, milestone 1 (27 Oct): spatial knowledge is now data. `packages/core/src/knowledge/office.v1.json` holds room rules, area rules, circulation widths, workstation clearances and validator thresholds, each citing a listed source (most are "icarus-default", honestly labelled; the minimum clear route and door opening cite the 2010 ADA Standards 403.5.1 and 404.2.3 as floors, not a compliance claim). A zod schema validates it and refuses a file that cites an unknown source or inverts a threshold. `catalog.ts`, the layout constants, the evidence thresholds and the furnishing clearances now read from it, and `describeKnowledge()` renders the same data as text for a model prompt, so the solver, the validator and the model cannot disagree. All 94 earlier tests passed unchanged, which shows the values were preserved.
- Propose-and-repair loop, milestone 2 (27 Oct): `packages/core/src/repair`. Programs carry `preferences` (extra neighbours, rooms to keep apart, an area bias that steers the solver while the validator still measures against the unbiased targets). `diagnose` turns a plan into structured issues (small or narrow room, missed adjacency, workspace density, seats short, daylight, reachability, a program that cannot fit); `issueCost` makes changes comparable. The loop (`refineDesign`) asks an advisor (a model) or the rules for a patch from a closed vocabulary (scale a room's area bias, prefer or avoid a neighbour, enlarge a shell whose size was only assumed), re-plans, and keeps the change only if the measured cost fell. It never touches the user's facts and is never worse than the start. First experiments changed the design: on programs that simply do not fit a stated shell nothing helps, my first area-based suggestions were wrong (an "enlarge to 25 x 16 m" still left 8 issues), so every suggestion is now planned and measured before it is offered (tight 40-person brief: enlarge to 28 x 18 m takes 12 open issues to 0; consultancy: enlarge to 25.5 x 16.5 m or drop 3 private offices), and an assumed shell is sized automatically (cost 173 to 3.6). 17 tests, with the two safety properties mutation-checked.
- Propose-and-repair loop, milestone 3 (27 Oct): the model's job, live. `packages/core/src/propose` defines `ProposalSchema` (what a model may add to a brief: unstated counts, restrained extra rooms, neighbour wishes, area bias, reasoned decisions) and `mergeProposal`, which can never override a stated fact and records every decision as a model assumption. Prompts are built from the knowledge file, include the stated facts, and carry an example answer that a test checks against the schema. `apps/edge` gained `POST /api/design/propose` and `/api/design/revise`: validated input, key server-side, answers re-validated against the closed schemas, one re-ask on an invalid answer, plain statuses (503 not configured, 429 busy, 502 mismatch) with nothing leaked. Live results on the free tier: `poolside/laguna-s-2.1:free` returns a valid proposal in about 9 s (one of two briefs mismatched once, which the loop tolerates) and a valid patch in about 2 s. Findings along the way: (1) a real bug in my transport, which called fetch as a method of itself; Node allows it, Workers and browsers throw "Illegal invocation", so it was reported as "network error" (fixed, with a test that fails on the old code); (2) the free reasoning model ignores a response schema and a reasoning-effort setting and rambles, so the exact output shape now goes in the instructions and JSON is extracted tolerantly then schema-validated; (3) of ten free models tried, only laguna-s answered validly and promptly, several were rate limited. Muse Spark is untested here (needs credits).
- Propose-and-repair loop, milestone 4 (27 Oct): in the product. A brief now goes: read the stated facts; ask the model (through the Worker) what was left open; merge without overriding anything stated; measure the proposal against the rules-only plan and set aside any room additions that make it worse (the first live run had accepted a private office into a tight shell before measuring, which a property test now guards, mutation-checked); plan, measure and repair; and if a failure is left, try six more layouts. The UI shows the live repair lines while it runs and a "How this was designed" card afterwards: each model decision with its reason (marked not used when set aside), what was refused because the brief states it, every repair tried (kept or not kept, by the model or the rules, with scores), and verified suggestions with Apply buttons. Everything degrades to the rules when the model service is absent, busy or wrong. Live end-to-end on the free model took about 20 s. The dev proxy now targets the Worker with the model key on port 8789 (`pnpm --filter @icarus/edge dev`).

- Change by words (27 Oct): `packages/core/src/edit`. A sentence becomes a few operations from a closed set (move a room to a side, swap two rooms, add or remove phone booths, lock or unlock a room, undo), read first by a small grammar and, failing that, by the model through `POST /api/design/edit`, which can only answer in the same operations. `applyEdit` works on the arrangement of rooms (stored in the program, so a reopened design reproduces it), plans every candidate, keeps only one that does what was asked, holds every locked room, introduces no new failure and keeps reception on the entrance lobby, and says in numbers what moved and what the score did; otherwise it leaves the plan alone and gives the reason. The first twelve-brief run (103 requests, no model) found a booth edit that cost a workstation seat past the failure line and swaps with reception refused too often (the check was too strict), both fixed and mutation-checked; final: 45 applied, 36 already in place, 22 refused with a reason, none introducing a failure. Swapping reception with a room in its own row is correctly refused, which is a real limit of the row layout (see `docs/EDITING.md`). In the app: a "Change it with words" box with example buttons, per-line results, lock chips and room labels on the floor plan; Undo reverses a whole sentence. Seen working in the browser, including undo and reopening a saved edited office. The model path ran live once (Llama 3.3 70B on Workers AI) and correctly said a "break area" is not a room it can add; it did not map "break area" to the lounge.
- Change by words, extended (27 Oct): resize a room ("make the kitchen bigger", by a percentage, "a bit", "much"), and add or remove meeting rooms ("add two meeting rooms for 10", "remove meeting room 2"), measured as before. Resizing splits the room's request so only that room gets its own area; a room held at its minimum width, or already above its target, is refused with the numbers. Adding tries every position and keeps the best one that passes; removal renumbers later rooms and carries the arrangement, locks and compared issues across. A 158-request run found a real bug (a warning tipped into a failure by an added meeting room was not counted as new); fixed with a test that fails on the old rule. Result: 86 applied, 36 already in place, 36 refused with a reason, none introducing a failure (`docs/EDITING.md`).
